# Design: GnomeCode — глубина плагинов: lifecycle + взаимодействие

Generated by /office-hours on 2026-10-12
Branch: main
Repo: GnomeDubl (локальный, без remote)
Status: APPROVED
Mode: Startup

## Problem Statement

GnomeCode (Tauri 2 + React 18 + Rust-мост, Windows) строится как замена
OpenCode-клиентов: «в нем нет кучи функционала, которого мне не достоет,
например легкого обновления плагинов и взаимодействия с ними» — владелец.
Этапы 1–2 старой карты сделаны (чат со стримингом и контекстом проекта,
плагины «в два клика» с правами/скоупами/автообновлением, провайдеры,
статистика, сравнение моделей). Следующий юнит работы определяет этот док:
углубление плагинного опыта вместо Фазы 2 (Workspaces/Skills/Tasks).

## Demand Evidence

- Единственное доказательство — сам владелец: «Я сам, ежедневно», злится,
  когда ломается (Q1). Внешних пользователей и платящих нет — стадия
  pre-product, подтверждена владельцем.
- Внешний спрос не проверен. Валидационная петля встроена в план
  (Success Criteria), а не отложена.

## Status Quo

- Ванильный OpenCode: плагины ставятся правкой `opencode.json`
  (`"plugin": [...]`), каталоги — GitHub-списки (awesome-opencode),
  обновления вручную, прав в GUI нет.
- Официальный OpenCode Desktop существует (клиент-сервер, плагины/MCP
  работают) — статус-кво включает и его.
- Владелец сегодня живёт в opencode-терминале; GnomeCode — облагораживание
  этого же сценария (Q2).

## Target User & Narrowest Wedge

- Q3 пропущен по правилу smart-skip: во всех ответах назван один человек —
  владелец. Первый внешний пользователь — гипотеза: Windows-разработчик,
  живущий в OpenCode с 2+ плагинами.
- Клин: GUI жизненного цикла плагинов (установка/обновление/права/скоупы)
  + ежедневное плагин-взаимодействие в чате (кнопки-команды, tool rows,
  инлайн-разрешения).

## Constraints

- Windows 10/11 x64 — первая и единственная платформа сейчас.
- Ядро — OpenCode server (ADR-0001): сессии, плагин-API, модели, снапшоты —
  нативно; свои движки не строим.
- Секреты — только в Credential Manager Windows; данные — %APPDATA%/GnomeCode.
- Стек зафиксирован: Tauri 2 + React 18 (src/) + Rust (src-tauri/);
  проверки: `npm run check` + `cargo test` (25+ тестов, зелёные).

## Premises

Согласованы владельцем 2026-10-12; №1 пересмотрена после второго мнения:

1. **Клин — плагинный lifecycle; удержание — ежедневное
   плагин-взаимодействие в чате.** Обе оси из цитаты владельца
   («обновления» И «взаимодействия»). Workspaces/Skills/Tasks — не
   следующий юнит (ревизия: исходная формулировка «не окно чата»
   обрезала вторую ось — оспорено субагентом, владелец принял правку).
2. «Замена всего OpenCode» — неверная рамка: GnomeCode выживает как
   альтернативный frontend с UX, которого нет у официальных клиентов
   (плагины, права, статистика). Гонка с официальным десктопом для
   одного разработчика проигрышна.
3. Первый внешний пользователь — Windows-разработчик в OpenCode с
   плагинами; валидация = он управляет плагинами через GnomeCode,
   а не через конфиги.
4. Ядро — OpenCode server; своё — только UX.

## Cross-Model Perspective

Второе мнение (внутренний субагент, свежий контекст; Codex CLI не
установлен):
- Steelman: GnomeCode — «App Store + диспетчер» для экосистемы плагинов
  OpenCode на Windows; GUI lifecycle нет ни у кого в категории, включая
  официальный десктоп.
- Ключевой инсайт: в цитате владельца обе оси — «обновление»
  (эпизодическая боль) и «взаимодействие» (ежедневная); построено же
  много вне списка болей (провайдеры, сравнение, темы).
- Оспорена предпосылка №1 — пересмотрена (см. выше).
- Прототип за 48 ч: «GnomeCode PM» — ампутация до однооконного менеджера
  (импорт opencode.json, каталог, «обновить всё» с diff прав, rollback,
  kill-switch), дистрибуция zip-ом, GIF 90 с + пост, цель — 5 внешних
  пользователей. Взято внутрь подхода A как валидационная кампания.

## Approaches Considered

- **A. «Глубина плагинов»** — lifecycle-глубина + плагины как главный
  экран чата; валидационная петля кампанией внутри. **Выбрано.**
- **B. «GnomeCode PM» (ампутация до менеджера)** — отвергнуто как
  отдельный путь: прячет поверхность удержания (чат), два продукта
  вместо одного; петля валидации перенесена внутрь A.
- **C. «Плагин-платформа»** (сразу дистрибуция + телеметрия) —
  отвергнуто: новая инфраструктура до первого внешнего пользователя;
  элементы C (Releases, счётчик событий) вошли в A по мере надобности.

## Recommended Approach

**A — «Глубина плагинов»** (Effort M, Risk Low-Med): закрывает обе оси
болли владельца, максимально переиспользует построенное (12 Rust-модулей
`plugins/`, ChatHeader, PluginApproval, PluginConfig, PluginUpdates),
измерим. Состав юнита:

1. Сводка прав при первом включении плагина (сцена H старой спеки —
   последний незакрытый кусок этапа плагинов).
2. Обновление с diff разрешений: какие новые права просит новая версия —
   allow/deny до включения.
3. Rollback версии в клик (снапшот конфига перед изменением) и
   kill-switch сломанного плагина без удаления.
4. Плагины как главный экран чата — поверхность ежедневного удержания.
   Поведение по элементам (минимальный срез юнита; всё строится на
   существующих компонентах, новых поверхностей не добавляется):
   - **Кнопка-команда**: плагин, подключённый к чату, объявляет команды
     (нативные команды OpenCode-плагина, источник — plugins/commands.rs);
     каждая рендерится кнопкой в шапке чата рядом с бейджем модели
     (ChatHeader), при переполнении — «+N»; клик исполняет команду через
     permission-слой, вызов виден в ленте как tool-строка.
   - **Tool-строка**: каждый вызов инструмента плагина — компактная строка
     в ленте («✓ GitHub · Read issue #241» / «⚠ … requires approval»),
     клик раскрывает детали (плагин, команда, аргументы, результат);
     источник — события ленты движка с метаданными tool-вызова (Feed).
   - **Инлайн-разрешение**: чувствительный вызов поднимает окно
     «Разрешить / Разрешить для этого чата / Отказать» поверх области
     чата (PluginApproval, существует); отказ — строкой «⚠ … denied»,
     вызов не идёт; правила категорий из Configure действуют без
     перезапуска.

5. Валидационная кампания (из B): GIF 90 с, пост в Discord OpenCode /
  r/opencodeCLI, цель 5 внешних пользователей, ≥3 остаются через неделю.

## Open Questions

- Источник каталога: курируемый index.json (старый BLOCKED: живого
  GitHub-источника нет) — нужен минимальный реестр для «Available».
- Kill-сигнал клина: GUI управления плагинами в официальном OpenCode
  Desktop — проверять раз в квартал.
- Формат телеметрии для проверки предпосылки №1 (события plugin-менеджера
  против чат-сессий) — opt-in, локальный сбор первым шагом.

## Success Criteria

- Сцена H: установка плагина показывает сводку прав, выбор действует на
  первый вызов (cargo + UI-проверка).
- Поверхность чата: команда реального плагина из каталога проходит
  end-to-end в чате — кнопка в шапке исполняет команду, вызов виден
  tool-строкой, чувствительный вызов поднимает инлайн-разрешение,
  отказ пишет «⚠ … denied» (cargo + UI-проверка, как для сцены H).
- Diff разрешений при обновлении + rollback + kill-switch работают
  на реальном плагине из каталога.
- GIF 90 с записан и опубликован; 5 внешних пользователей
  «Windows + OpenCode + плагины»; ≥3 через неделю управляют плагинами
  через GnomeCode, не через JSON.
- Счётчик событий (opt-in): plugin-lifecycle vs chat-сессии — данные для
  проверки предпосылки №1.

**Как измеряется кампания** (ретеншн — самоотчётом, не телеметрией):
- «5 внешних пользователей» — список из 5 имён с контактами заведён до
  поста; каждый установил сборку и подтвердил установку ответом
  (Discord/Reddit DM).
- «≥3 через неделю» — через 7 дней каждому из пяти отправлен один вопрос
  («чем сейчас ставишь/обновляешь плагины?»); удержанием считается
  ответ «через GnomeCode»; ответы сохранены дословно в этот док.
- Публикация GIF — ссылка на пост (Discord OpenCode / r/opencodeCLI).

### R2-1 — consistency (minor)

**Problem**

> Status Quo still states plugin catalogs are «каталоги — GitHub-списки (awesome-opencode)» while Open Questions still states «старый BLOCKED: живого GitHub-источника нет». The two sections still disagree about whether a live GitHub catalog source exists, and the intended distinction (curated human README lists vs a machine-readable maintained index) is still not stated. Persisting from R1-4; neither passage changed in this round.

**Remedy**

> State the intended distinction: human-curated README lists exist (awesome-opencode), but no machine-readable, maintained index.json source does — which is why the minimal curated registry is needed.

### R2-2 — feasibility (minor)

**Problem**

> One-click rollback is still specified only as «снапшот конфига перед изменением» (Recommended Approach, item 3). The document still never states the install-source semantics (version-pinned package specs vs mutable git/file sources) or whether prior artifacts are cached locally, so it remains unverified that a config snapshot alone can restore an older plugin version. Persisting from R1-5.

**Remedy**

> State the assumption rollback relies on (e.g., installs are version-pinned package specs, or artifacts are cached locally on install and restorable), or scope rollback to what that assumption supports.

### R2-3 — feasibility (minor)

**Problem**

> «Effort M, Risk Low-Med» is still asserted without breakdown or justification while the unit commits five engineering components plus a minimal plugin registry, CI + GitHub Releases setup, opt-in telemetry, and a community campaign with a 90-second GIF. The label remains an unsupported estimate the owner cannot sanity-check. Persisting from R1-6.

**Remedy**

> Add a one-line justification for the estimate, or split it (engineering core vs registry/CI infrastructure vs campaign) so the owner can sanity-check scope against effort.

### R2-4 — completeness (minor)

**Problem**

> The minimal catalog registry remains a hard dependency of committed verification — the update-diff/rollback/kill-switch criterion and the new chat-surface criterion both require a «реальный плагин из каталога», and the «Available» list needs the registry — yet its minimal viable contents are still undefined: how many plugins, whether entries carry versioned artifacts and machine-readable permission/scope metadata (required for the permission diff). Persisting from R1-7; Open Questions and Dependencies still say only «открыть или собрать минимальный».

**Remedy**

> Define the minimal registry the unit needs: e.g., 1–3 real plugins with versioned download sources and machine-readable permission declarations.

### R2-5 — clarity (minor)

**Problem**

> The new retention measurement asks each user only «чем сейчас ставишь/обновляешь плагины?», but the Success Criterion it claims to measure is broader: «≥3 через неделю управляют плагинами через GnomeCode, не через JSON», and the wedge defines management as установка/обновление/права/скоупы. An answer «через GnomeCode» to the install/update question verifies a narrower behavior than the criterion asserts (a user could install via GnomeCode yet still edit JSON for permissions).

**Remedy**

> Either narrow the criterion wording to installs/updates via GnomeCode, or extend the single question (e.g., «чем сейчас ставишь, обновляешь и настраиваешь плагины?») so the self-report matches what the criterion claims.

### R2-6 — clarity (minor)

**Problem**

> The new measurement requires the list of 5 names with contacts to be created «до поста», while the campaign's stated acquisition channel for the 5 external users is the Discord/Reddit post itself (component 5; Distribution Plan). As written it is ambiguous whether the 5 must be recruited before the post (making the post irrelevant to the metric) or recruited from post/DM respondents and then tracked — which changes what «5 внешних пользователей» validates (organic pull from the post vs pre-recruited volunteers).

**Remedy**

> Clarify the sequencing: either the 5 are recruited from post/DM responses and then recorded in the tracked list, or pre-recruitment before posting is intentional and the post is supplementary distribution.

### R2-7 — completeness (minor)

**Problem**

> The new chat-surface criterion verifies that the inline permission dialog appears and the deny path (отказ → «⚠ … denied»), but not the grant paths — neither «Разрешить» letting the sensitive call proceed nor the distinct session-persistence behavior of «Разрешить для этого чата» that component 4 commits to. A broken or non-persistent grant path could pass every success criterion.

**Remedy**

> Extend the criterion by one clause: approving the inline permission («Разрешить» / «Разрешить для этого чата») lets the sensitive call proceed, and the «для этого чата» choice is honored for the rest of the chat session.
