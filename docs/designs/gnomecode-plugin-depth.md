## Implementation plan

### Problem Statement

GnomeCode (Tauri 2 + React 18 + Rust-мост, Windows) строится как замена
OpenCode-клиентов: «в нем нет кучи функционала, которого мне не достоет,
например легкого обновления плагинов и взаимодействия с ними» — владелец.
Этапы 1–2 старой карты сделаны (чат со стримингом и контекстом проекта,
плагины «в два клика» с правами/скоупами/автообновлением, провайдеры,
статистика, сравнение моделей). Следующий юнит работы определяет этот док:
углубление плагинного опыта вместо Фазы 2 (Workspaces/Skills/Tasks).

### Demand Evidence

- Единственное доказательство — сам владелец: «Я сам, ежедневно», злится,
  когда ломается (Q1). Внешних пользователей и платящих нет — стадия
  pre-product, подтверждена владельцем.
- Внешний спрос не проверен. Валидационная петля встроена в план
  (Success Criteria), а не отложена.

### Status Quo

- Ванильный OpenCode: плагины ставятся правкой `opencode.json`
  (`"plugin": [...]`), каталоги — GitHub-списки (awesome-opencode),
  обновления вручную, прав в GUI нет.
- Официальный OpenCode Desktop существует (клиент-сервер, плагины/MCP
  работают) — статус-кво включает и его.
- Владелец сегодня живёт в opencode-терминале; GnomeCode — облагораживание
  этого же сценария (Q2).

### Target User & Narrowest Wedge

- Q3 пропущен по правилу smart-skip: во всех ответах назван один человек —
  владелец. Первый внешний пользователь — гипотеза: Windows-разработчик,
  живущий в OpenCode с 2+ плагинами.
- Клин: GUI жизненного цикла плагинов (установка/обновление/права/скоупы)
  + ежедневное плагин-взаимодействие в чате (кнопки-команды, tool rows,
  инлайн-разрешения).

### Constraints

- Windows 10/11 x64 — первая и единственная платформа сейчас.
- Ядро — OpenCode server (ADR-0001): сессии, плагин-API, модели, снапшоты —
  нативно; свои движки не строим.
- Секреты — только в Credential Manager Windows; данные — %APPDATA%/GnomeCode.
- Стек зафиксирован: Tauri 2 + React 18 (src/) + Rust (src-tauri/);
  проверки: `npm run check` + `cargo test` (128 тест-функций в 23 файлах).

### Premises

Согласованы владельцем 2026-10-12; №1 пересмотрена после второго мнения:

1. **Клин — плагинный lifecycle; удержание — ежедневное
   плагин-взаимодействие в чате.** Обе оси из цитаты владельца
   («обновления» И «взаимодействия»). Workspaces/Skills/Tasks — не
   следующий юнит (ревизия: исходная формулировка «не окно чата»
   обрезала вторую ось — оспорено субагентом, владелец принял правку).
2. «Замена всего OpenCode» — неверная рамка: GnomeCode выживает как
   альтернативный frontend с UX, которого нет у официальных клиентов
   (плагины, права, статистика). Гонка с официальным десктопом для
   одного разработчика проигрышна.
3. Первый внешний пользователь — Windows-разработчик в OpenCode с
   плагинами; валидация = он управляет плагинами через GnomeCode,
   а не через конфиги.
4. Ядро — OpenCode server; своё — только UX.

### Cross-Model Perspective

Второе мнение (внутренний субагент, свежий контекст; Codex CLI не
установлен):
- Steelman: GnomeCode — «App Store + диспетчер» для экосистемы плагинов
  OpenCode на Windows; GUI lifecycle нет ни у кого в категории, включая
  официальный десктоп.
- Ключевой инсайт: в цитате владельца обе оси — «обновление»
  (эпизодическая боль) и «взаимодействие» (ежедневная); построено же
  много вне списка болей (провайдеры, сравнение, темы).
- Оспорена предпосылка №1 — пересмотрена (см. выше).
- Прототип за 48 ч: «GnomeCode PM» — ампутация до однооконного менеджера
  (импорт opencode.json, каталог, «обновить всё» с diff прав, rollback,
  kill-switch), дистрибуция zip-ом, GIF 90 с + пост, цель — 5 внешних
  пользователей. Взято внутрь подхода A как валидационная кампания.

### Approaches Considered

- **A. «Глубина плагинов»** — lifecycle-глубина + плагины как главный
  экран чата; валидационная петля кампанией внутри. **Выбрано.**
- **B. «GnomeCode PM» (ампутация до менеджера)** — отвергнуто как
  отдельный путь: прячет поверхность удержания (чат), два продукта
  вместо одного; петля валидации перенесена внутрь A.
- **C. «Плагин-платформа»** (сразу дистрибуция + телеметрия) —
  отвергнуто: новая инфраструктура до первого внешнего пользователя;
  элементы C (Releases, счётчик событий) вошли в A по мере надобности.

### Recommended Approach

**A — «Глубина плагинов»** (Effort M, Risk Low-Med): закрывает обе оси
болли владельца, максимально переиспользует построенное (12 Rust-модулей
`plugins/`, ChatHeader, PluginApproval, PluginConfig, PluginUpdates),
измерим. Состав юнита (пополнен CEO-фазой autoplan 2026-10-14, см. Review record):

1. Сводка прав при первом включении плагина (сцена H старой спеки —
   последний незакрытый кусок этапа плагинов).
2. Обновление с diff разрешений: какие новые права просит новая версия —
   allow/deny до включения; кнопка «Обновить всё» со сводкой по каждому
   плагину (CE-2). Связка с существующим автообновлением (запуск): новых
   прав нет — обновляется тихо, как сегодня; появились — плагин получает
   статус «ждёт одобрения прав»; diff — на вкладке Updates, бейдж
   увеличивает счётчик ждущих одобрения (Я-2). Автообновление с diff
   прав работает только для плагинов
   из реестра; вне-реестровые (импортированные или установленные до
   реестра) не автообновляются — статус «обновление вручную» (1.1).
   «Обновить всё» обрабатывает плагины независимо: отказ в правах
   оставляет один плагин на текущей версии (пометка «ждёт одобрения»),
   остальные обновляются.
3. Rollback версии в клик: снапшот конфига перед изменением + локальный
   кэш артефактов версий при установке (CE-3); kill-switch сломанного
   плагина без удаления (Disable уже в manage.rs). Границы rollback:
   откат доступен для версий, прошедших через кэш GnomeCode (установка/
   обновление из GnomeCode); для версий до кэша кнопка неактивна с
   подсказкой «версия до GnomeCode», а если предыдущая версия есть
   в реестре — предлагается установка из реестра. Снапшот включает
   и permissions-конфиг: rollback восстанавливает права/скоупы на
   момент снапшота (1.3). Kill-switch в живом
   чате: кнопки команд исчезают из шапки сразу, летящие вызовы
   завершаются, новые блокируются строкой «плагин отключён».
4. Импорт существующей конфигурации OpenCode при первом запуске (CE-1):
   источник — `%USERPROFILE%\.config\opencode\opencode.json`
   (наблюдаемый путь OpenCode на Windows; при отсутствии — проверяется
   `%APPDATA%\opencode\opencode.json`; проектные opencode.json не
   трогаем) (Ф-1); ре-импорт на каждом запуске
   добавляет только новые записи — ключ дедупликации имя npm-пакета,
   существующие записи не перезаписываются (1.2); импортированный
   плагин, найденный в реестре (id = имя npm-пакета), переходит под
   управление реестра — автообновление с diff (П-1); импортированные
   входят как «установленные, отключённые», включение каждого проходит
   сцену H; скоуп не назначается (Chat по умолчанию при подключении).
5. Минимальный курируемый реестр каталога (CE-4): 1–3 реальных плагина,
   у каждого ≥1 команда и ≥1 инструмент, требующий прав (кандидаты —
   плагины уведомлений из экосистемы opencode; финальный выбор при
   сборке реестра по этому критерию). Хостинг: index.json публикуется
   raw-файлом в GitHub-репозитории GnomeCode (тот же, что Releases
   приложения), клиент тянет его по CATALOG_URL. Схема записи (3.1,
   дополнена дизайн-фазой): `id, version, artifact_url, sha256,
   permissions, scopes, commands, icon_url (необяз., sha-проверяемый),
   permission_descriptions (необяз., человеческие формулировки «зачем»)`;
   fallback иконки — плитка с инициалами плагина или глиф-пазл из
   glyphs.css (F16); fallback формулировок — карта id→текст в
   приложении, «неизвестное разрешение: \<id\> · проверить вручную»
   (F17). GnomeCode проверяет хэш перед установкой/
   обновлением/rollback, несовпадение — явный отказ (CE-3/CE-5, закрывает
   целостность).
6. Плагины как главный экран чата — поверхность ежедневного удержания.
   Поведение по элементам (минимальный срез юнита; всё строится на
   существующих компонентах, новых поверхностей не добавляется):
   - **Кнопка-команда**: плагин, подключённый к чату, объявляет команды
     (нативные команды OpenCode-плагина, источник — plugins/commands.rs);
     каждая рендерится кнопкой в шапке чата рядом с бейджем модели
     (ChatHeader), при переполнении — «+N»; клик исполняет команду через
     permission-слой, вызов виден в ленте как tool-строка.
   - **Tool-строка**: каждый вызов инструмента плагина — компактная строка
     в ленте («✓ GitHub · Read issue #241» / «⚠ … requires approval»),
     клик раскрывает детали (плагин, команда, аргументы, результат);
     источник — события ленты движка с метаданными tool-вызова (Feed).
   - **Инлайн-разрешение**: чувствительный вызов поднимает окно
     «Разрешить / Разрешить для этого чата / Отказать» поверх области
     чата (PluginApproval, существует); отказ — строкой «⚠ … denied»,
     вызов не идёт; «Разрешить» пропускает вызов, «для этого чата»
     помнится до конца сессии чата движка (грант хранится на чат и
     переживает рестарт приложения); правила категорий из Configure
     действуют без перезапуска. «+N» открывает тот же список команд
     вертикальным меню.
7. Счётчик доступных обновлений на бейдже «Плагины» (CE-5, delight):
   источник — проверка каталога (запуск приложения + кнопка «Обновить
   каталог» на вкладке Available; автопроверка отложена — CE-8).
   Каталог недоступен (сеть/CATALOG_URL) — тихий отказ; бейдж и вкладка
   Available показывают время последней успешной проверки (1.4).
8. Валидационная кампания (из B): GIF 90 с, пост в Discord OpenCode /
   r/opencodeCLI; пять внешних пользователей рекрутируются из ответов
   на пост и заносятся в трекинг-список; ≥3 через 7 дней отвечают
   «через GnomeCode» на вопрос «чем сейчас ставишь, обновляешь и
   настраиваешь плагины?» (самоотчёт, дословно в док).
9. Событийный счётчик (П-3): локальный JSONL в папке данных, opt-in
   в Настройках, без сети; события: install, update, rollback, enable,
   disable, command, chat-session (3.2) — данные для проверки
   предпосылки №1.

### UI-спецификация юнита (design-фаза autoplan, 2026-10-14)

**Первый запуск** (критично для GIF): экран «В вашей конфигурации
OpenCode найдено N плагинов» — список (иконка, имя, версия), чекбоксы
**по умолчанию сняты**; строка разворачивается инлайн в контент сцены H
(источник, версия, ≤3 пункта прав с «зачем»); мастер-кнопка «Включить
выбранные» = единое комбинированное одобрение, снятие чекбокса =
отказ для этого плагина — каскада диалогов нет, сцена H сохранена
(F2); N=0 — без модалки, строка в пустом чате «Установите первый
плагин →» (F9); «обработано» = явное действие (Включить или
«Пропустить») (F10); новые записи при следующих запусках — тост
«Найден новый плагин · включить» + запись в менеджере как отключённая;
битый конфиг — «Распознано N из M».

**Шапка чата**: порог 3 кнопки-команды + «+N»; порядок = алфавит по
имени команды (предсказуем, F4); содержимое кнопки = иконка плагина +
имя команды, max-width с ellipsis и tooltip с полным именем (F18);
0 команд у подключённых — блока нет; 0 подключённых — шапка не меняется;
упавший плагин — серая кнопка с глифом ошибки + tooltip, однократная
строка в ленте «плагин N не запустился · подробнее» (F11).
«+N»: вертикальное меню от кнопки, Esc/клик-мимо закрывает, скролл
при >10, живая синхронизация с командами.

**Очередь инлайн-разрешений** (F5): чувствительные вызовы при
стриминге сериализуются FIFO; модалка показывает «1 из N»; лента
продолжает рендерить незаблокированные строки позади.

**Kill-switch из чата**: контекстное меню кнопки-команды (шеврон) и
пункт в раскрытой tool-строке — один клик без подтверждения; тост
«Плагин отключён · **Отменить**» (F13). В раскрытии tool-строки —
«Откатить на \<версию\>», когда версия есть в кэше (F14). Rollback при
живом чате = правила kill-switch (кнопки исчезают, летящие завершаются)
+ тост «GitHub 2.1.0 → 2.0.4»; применение — спиннер на кнопке;
sha-несовпадение — inline-ошибка на карточке + retry (F8).

**Diff прав — карточка на плагин**: «Что нового» человеческими
формулировками («Плагин просит новую возможность: читать файлы вне
папки проекта»); добавленное — added-цвет из tokens.css, убранное —
приглушённо; максимум 3 пункта, «Ещё N» раскрывается инлайн (не
модалкой), кнопка «Обновить» неактивна до первого раскрытия (F15);
кнопки «Обновить / Оставить текущую». «Обновить всё» = стек карточек;
per-card статусы: скачивается / проверяется / ждёт одобрения / ошибка
+ retry; итог — тост «Обновлено N · ждёт M · ошибок K» (F7).

**Tool-строки — 5 состояний, 4 глифа** (F6): в полёте (спиннер) /
✓ успех / ✗ ошибка («ошибка») / ✗ отклонено («отклонено вами») /
⚠ требует одобрения; глифы из glyphs.css с семантическими цветами
tokens.css (не эмодзи, обе темы); раскрытие — детали до 20 строк,
дальше «Показать полностью»; индикатор активного гранта в раскрытии;
пункты «Отключить плагин» и «Откатить».

**Бейдж «Плагины» — единая семантика** (5.1): считает только требующее
решения пользователя («ждёт одобрения прав»). Тихие обновления в бейдж
не попадают по определению. Ошибка применения — error-статус на
карточке, не число. Неудачная проверка каталога бейдж не меняет.

**Сцена H (сводка прав)**: максимум 3 пункта с пояснением «зачем»,
остальное свёрнуто; сверху источник и версия; для импортированных —
пометка «источник: ваш opencode.json · целостность не проверена»;
формулировки «зачем» — из permission_descriptions реестра либо карта
id→текст в приложении, fallback «неизвестное разрешение: \<id\> ·
проверить вручную» (F17).

**Инлайн-разрешение — клавиатура**: фокус-ловушка, Esc = Отказать,
Enter по умолчанию НЕ «Разрешить» (дефолт — нейтрально); микроподпись
«запомнено для этого чата, включая перезапуски»; тач-таргеты ≥44px.

**Каталог — состояния**: Available — skeleton при загрузке; оффлайн —
inline-ошибка + retry + «данные от \<дата\>» (кэш последнего index.json);
пустая вкладка (всё установлено) — CTA «Предложить плагин в реестр» и
подпись «реестр курируемый, пока маленький»; sha-несовпадение —
inline-блок на карточке «Целостность артефакта не подтверждена» + retry.

**Статусы плагина в менеджере**: таблица «статус × цвет/иконка ×
доступные действия»: установлен-включён / отключён-пользователем /
импортирован-отключён / ждёт-одобрения-прав / не-запустился.

**Узкое окно 1024×640**: кнопки-команды сворачиваются в «+N» раньше
(порог 2), бейдж и меню не меняются.

### DX-спецификация юнита (DX-фаза autoplan, 2026-10-14)

**Дистрибуция и доверие (F-DX-1, критично для кампании):** рядом с
релизом публикуется sha256 установщика; в README и посте — скриншот
SmartScreen «More info → Run anyway»; после валидации — подпись
(Azure Trusted Signing) или winget (TODO). Установщик и zip проходят
проверку хэша как и артефакты плагинов.

**Движок (F-DX-2):** используется установленный `opencode` пользователя
(кампанейская персона — уже в OpenCode, ноль шагов); при старте —
проверка здоровья движка (версия/запуск), ошибка = problem + retry +
ссылка на troubleshooting.

**Провайдеры (F-DX-3):** GnomeCode читает конфиг и аутентификацию
opencode — существующий пользователь не настраивает модели заново;
это явно сказано в README.

**Docs-деливераблы юнита (F-DX-4):** README (установка, SmartScreen,
где данные, удаление), privacy-заметка (счётчик — локальный JSONL,
opt-in, без сети), одностраничный гайд автора плагина (объявить
commands/permissions), схема реестра с примером записи + JSON-Schema
файлом.

**Побег-хэтчи (F-DX-5/8/9/11):** Настройки: «тихие обновления»
(вкл/выкл, default on), «кэш версий: N МБ · очистить», переопределение
CATALOG_URL (file://локальный путь, «расширенное»); per-plugin:
«не обновлять автоматически» и «управлять вручную» — захват реестром
