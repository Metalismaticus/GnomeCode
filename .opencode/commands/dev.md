Прочитай план @docs/designs/gnomecode-plugin-depth.md — раздел «Порядок исполнения».

$ARGUMENTS

Правила работы:

1. Аргументы:
   - не задан — возьми первую непроверенную задачу из «Порядка исполнения» (без `[x]`) и делай только её;
   - `все` (или `all`) — режим конвейера: работай задачи по порядку одну за другой, пока хватает контекста; между задачами не жди указаний; когда контекст на исходе — последний шаг: gstack-context-save и короткий отчёт, что закрыто и что следующая;
   - имя задачи (например, B2 или T1) — работай только её.
2. Задачи владельца T9/T10 пропускаешь — их делает человек.
3. Одна задача за раз. Конвейер каждой задачи строго такой:
   а) реализация по плану и UI-спецификации из него;
   б) прогони навык gstack-review на своём дифе (изменившиеся файлы против HEAD);
   в) прогони навык gstack-qa на fixture-странице приложения: `npm run dev` (порт 5173), нужные состояния задаются URL-параметрами `?состояние=...` (см. src/viewparams.ts); QA-отчёт прикладываешь;
   г) `npm run check` зелёный — затем один коммит с сообщением вида «B2: поиск по чатам в сайдбаре»;
   д) отметь задачу `[x]` в docs/designs/gnomecode-plugin-depth.md тем же коммитом.
4. Если задача упёрлась в гейт (ET0 решает судьбу п.6, реестр нужен до diff-прав) — выполни гейт первым, результат запиши в план.
5. В режиме «все»: после каждой закрытой задачи сразу бери следующую; не останавливайся на отчётах между задачами. Останов только: всё закрыто, упёрся в гейт, ждущий человека (T9/T10, или гейт решён — продолжай), или контекст кончается.
6. Не расширяйscope за пределы задачи. Новые идеи — одной строкой в конец плана, раздел «Кандидаты», не реализуешь.

Проверки: `npm run check`; cargo-тесты затронутых модулей (`cargo test --manifest-path src-tauri/Cargo.toml --test <имя>`).
