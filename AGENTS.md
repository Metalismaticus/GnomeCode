# GnomeCode

Десктопный AI-клиент для разработки: чат с моделями поверх ядра OpenCode,
привязанный к проектам, с плагинами «в два клика» и политикой безопасности
на уровне чата. Windows 10/11 x64 (другие платформы — позже).

## Стек

- GUI: **Tauri 2** (Rust-бэкенд, `src-tauri/`) + **React 18 + TypeScript** (Vite, `src/`), strict-типы.
- Ядро: **OpenCode server** (`opencode serve`, HTTP API) — агентный движок, модели, tools, MCP. Своего движка нет: всё через типизированный API-клиент в `src-tauri/` (анти-коррозионный слой, ADR-0001 `docs/DECISIONS.md`).
- Инструменты: Node 22, npm 10, Rust (rustup), Python 3.13 (страж и `tools/`).
- Целевая платформа первой версии: Windows 10/11 x64. Сборка — `npm run tauri build` (NSIS/MSI), до первого выпуска не настроена.

## Каталоги

```
src/           интерфейс (React): колонки, чат, панели; стили-токены в src/styles
src-tauri/     бэкенд Tauri: мост к OpenCode server, файловые операции, права
docs/          документация проекта (замысел — docs/SPEC/, решения — docs/DECISIONS.md)
docs/refs      образцы вида: референсы интерфейса, снимки, листы
docs/orders    виды заказов: макеты экранов, журнал происхождения
docs/prompts   готовые заказы по партиям
docs/specs     спецификации экранов от designer (пункты [ui])
tests/         полигон: проверки по одной в tests/checks/
tools/         скрипты процесса (не продукт): проверки документов и кода
```

## Запуск и проверка

```bash
npm run tauri dev        # окно приложения для владельца
npm run build            # быстрая проверка: tsc (strict) + vite build
cargo check              # быстрая проверка: Rust-бэкенд (в src-tauri)
python -X utf8 tools/code_check.py --changed   # здоровье кода
```

Вердикт честный: nonzero-код возврата у `npm run build` и `cargo check` —
реальная ошибка; предупреждения компилятора не валят команду. Полная таблица
— `docs/TESTING.md`.

## Команды

| Команда | Чат | Когда звать |
|---|---|---|
| `/studio/idea <заметка или список>` | замысла | разобрать идеи, баги и вопросы, сверить с кодом и после подтверждения внести в документы; код не писать |
| `/studio/roadmap [следующий\|пересмотр\|прогноз]` | замысла | разложить весь замысел на этапы от «что увидит игрок»: каждая система — в этапе, «Потом» или «Не делаем»; `следующий` — начать этап «следом», `пересмотр` — замысел сменился, `прогноз` — сколько ещё по вашему темпу |
| `/studio/fault <симптом>` | замысла | что-то сломалось — записать в BUGS, причину предложить, но не чинить |
| `/studio/order <вид> <что>` | замысла | нужен макет или другой заказ — собрать заказ и записать долг; `/studio/mockup` — короткая форма макета |
| `/studio/need [раздел]` | замысла | показать все долги владельца с готовыми промтами; решения спросить окнами и записать ответы |
| `/studio/board` | любой | один экран: что ждёт вас, партия, очередь, баги, неладное; ничего не правит |
| `/studio/start [пункт\|all]` | разработки | выполнить первый пункт очереди, названный пункт или всю доступную очередь; каждый одобренный шаг — контрольный коммит |
| `/studio/done [кроме\|только ...]` | разработки | владелец проверил результат — принять партию или её часть, непринятое откатить с его причиной |
| `/studio/add [папка]` | разработки | разобрать пришедшие файлы заказов: узнать, проверить, записать |
| `/studio/check [имя]` | разработки | прогнать проверки и разобрать провалы |
| `/studio/parallel [N\|проверки M\|проверить]` | разработки | сколько пунктов пишется разом (0/1 — по одному; на один запуск — `/studio/start all xN`) и сколько тяжёлых проверок, обычно 1 |
| `/studio/retro` | разработки | что в партии пошло не так и что из этого урок проекта, а что — процесса; без окон, сам в конце `/studio/done`, вручную — за несколько партий |
| `/studio/release [версия]` | разработки, вне партии | выпустить версию: сборка, её проверка, тег, заметки словами пользователя; площадка — только по вашему «да» |
| `/studio/setup обновить` | любой, вне партии | плагин обновился — перенести новый шаблон процесса в документы проекта (во время партии — только недостающие `tools/`) |

## Два чата

Замысел и разработка ведутся в разных чатах, но в одной папке и на одной ветке
`main`. Разделяет их не папка, а то, что каждый трогает:

| | Чат замысла | Чат разработки |
|---|---|---|
| команды | `/studio/idea`, `/studio/roadmap`, `/studio/fault`, `/studio/order`, `/studio/need` | `/studio/start`, `/studio/done`, `/studio/add`, `/studio/check`, `/studio/parallel`, `/studio/retro`, `/studio/release` |
| что меняет | только `.md` (документы, заказы, паспорта образцов), картинки-образцы и листы разбора в `docs/refs/`; `/studio/roadmap` — блоки `status` и `pitch` README и About в «Git» `AGENTS.md` | код, данные, проверки, `docs/BATCH.md`, строки приёма в `docs/orders/ledger.md` (`/studio/add`), вопросы пунктов в «Решения» `docs/BLOCKED.md`; в `docs/refs/` — листы сравнения, принятые снимки, выбор варианта в «Журнале» паспорта; `/studio/release` — `docs/releases/`, `CREDITS.md`, «Выпуски» в `docs/DECISIONS.md`, «сборка», «Выпуск» и «Окружение» в `docs/TESTING.md`, `.gitignore`, номер версии; блоки README — `/studio/done`, `/studio/release`; About в «Git» — `/studio/release` |
| продукт | не запускает никогда (скрипты `tools/` над документами и кодом — `roadmap_check.py`, `look_sheet.py`, `refs_check.py`, `code_check.py` (только читает) — не продукт, их можно): причину ищет по коду, замер отдаёт в очередь | запускает и меряет — руками субагентов |
| коммиты | свои `.md` и образцы — сразу в `main` | каждый зелёный пункт — сразу в `main`; выпуск — тег `v<версия>` |

Рабочей ветки нет намеренно: у папки одна текущая ветка, и коммиты чата
замысла легли бы в ветку разработки. Порядок держат правила:

- каждый коммитит только свои файлы, поимённо — не `git add -A`, `git add .`,
  `git stash`, `git reset --hard`, `git checkout .`: в папке лежит чужая
  незакоммиченная работа (страж коммитов плагина это блокирует);
- во время партии чат разработки из документов правит только `docs/BATCH.md`,
  «Журнал» паспорта образца (выбор варианта), строки пришедших
  файлов в `docs/orders/ledger.md` (`/studio/add`) и вопросы пунктов в «Решения»
  `docs/BLOCKED.md` (ответ даёт `/studio/need`), остальные — при `/studio/done`; идеи,
  внесённые в очередь во время партии, ждут следующей партии;
- владелец высказался о пункте текущей партии — чат замысла пишет к пункту в
  `docs/ROADMAP.md` (у бага — в `docs/BUGS.md`) строку «Замечание владельца во
  время партии (<дата>): «…»»; `/studio/done` показывает их перед принятием;
- пришедшее `/studio/add` в очередь не ставит: строки для `ROADMAP.md` и `BLOCKED.md`
  он пишет в раздел «Пришло — внести в очередь» файла `docs/BATCH.md`, а
  переносит их и выбирает место чат замысла;
- чат разработки — тот, где звали `/studio/start`; в любом другом «делай» разработку
  не запускает.

## Как приходит работа

Сообщение через `/studio/idea` — всегда разбор: показать владельцу, как поняты пункты,
и перенести в документы только после подтверждения. Даже слово «сделай» внутри
такого сообщения не разрешает начинать реализацию.

Список в обычном сообщении — **не наряд на работу**. Каждый пункт сначала
уходит туда, где ему место:

| Что прислали | Куда |
|---|---|
| сломано у пользователя | `docs/BUGS.md` — симптом, причина, чем подтверждена |
| новая функция или переделка | `docs/ROADMAP.md`, разбитое на куски |
| образец вида: скрин, приложение, «как в X» | `docs/refs/<тема>.md` — паспорт образца: разбор агентом `reference` до вопросов; что владельцу важно — из его слов, окно «что вам нравится» — только если слова этого не говорят |
| концепт стиля интерфейса: картинка, ТЗ на стиль | `/studio/idea`: паспорта тем и «Правила стиля» `docs/refs/INDEX.md`; замысел не меняет |
| про замысел продукта | `docs/CONCEPT.md`; новая система — и строкой «Покрытия замысла»; весь замысел или план — `/studio/roadmap` |
| нужен заказ или решение | `docs/BLOCKED.md` |
| пришёл файл заказа | `/studio/add` в чате разработки |

Общая очередь выстраивается **сама** в `docs/ROADMAP.md` — это работа чата, а
не вопрос владельцу (состав и порядок этапов — его, `/studio/roadmap`). Баги стоят в
ней ссылками на `BUGS.md` вперемешку с разработкой, описание не копируется.

Приоритет — по совокупности, а не по ярлыку «баг»:

1. пользователь не может пользоваться продуктом, теряет данные или управление;
2. скольких и как часто задевает проблема;
3. что разблокирует другие пункты;
4. подтверждено ли поведение замером;
5. стоимость работы — только после влияния и уверенности.

Пункт, которому нужен ответ, файл или проверка владельца, остаётся в очереди с
пометкой `ждёт` и пропускается при автоматическом выполнении. `/studio/start all`
идёт без присмотра: порядок работы и вариант `[вид]`, ближе всех к образцу,
решает сам (строка «Решил сам» — отменить при `/studio/done`), вопрос «что делать»
отдаёт в `/studio/need` и берёт другой пункт, окна — только в конце и только
вопросы, которые нельзя отложить; вид владелец судит в `/studio/done`.

В чате разработки обычное **«делай»** равно `/studio/start`, **«делай всё»** — `/studio/start
all`, **«сделай уборку»** — `/studio/start all уборка`. Спрашивать «с чего начать?»
не нужно: ответ следует из очереди.

## Метки пунктов очереди

Состояние: `[можно]` — бери; `[ждёт …]` — нужен ответ, файл, снимок или
проверка владельца; `[ждёт образца]` — паспорт темы в `docs/refs/` не
подтверждён владельцем; `[ждёт «да»]` — пункт необратим (формат хранения,
удаление содержимого, выпущенное); `[ждёт проверок]`, `[ждёт уборки]` — ждёт
не владельца, а полигона или уборки перед ним (`[можно]` возвращают `/studio/idea`
и `/studio/done`); `[ждёт света]`, `[ждёт приёма]` — не долг владельца.
Пометка `[предварительно]` — владелец сказал с оговоркой («наверное»,
«кажется»), это не его решение. Этап: `[этап N]` — пункт из этапа N «Этапов»
`docs/ROADMAP.md`; есть «Этапы» — метка у каждого пункта очереди, кроме
`Уборка:`, и в очереди только этап `идёт`. Маршрут:

| Метка | Кто делает |
|---|---|
| `[код]`, `[баг]` | цепочка `executor`: `executor-prep` (бриф) → `executor-code` (красное доказательство и реализация) → `executor-finish` (проверки, снимки, итог) → `reviewer` с полной проверкой; в `/studio/start all` — `reviewer-fast`, лёгкий режим, полная одна в конце партии |
| `[ui]` | только экраны интерфейса: `designer` пишет спецификацию экрана → цепочка `executor` (prep → code → finish) → `reviewer` со снимками |
| `[данные]` | цепочка `executor` → `reviewer` с проверкой пункта и быстрой проверкой, без полной |

Пункт другой метки, критерий которого про вид, проверяющий снимает в месте из
«Как увидеть» или записи бага; без снимка, когда снять можно, такой пункт не
одобряется; снять нечем — одобрение с пометкой «вид не проверен».

## Правила проекта

- **Ядро — OpenCode server, не свой движок.** GUI не содержит агентной логики:
  модели, сессии, tools, MCP — только через типизированный API-клиент в
  `src-tauri/src/opencode/`; React-компоненты не зовут HTTP напрямую (ADR-0001).
- **Permission layer обязателен.** Любой вызов инструмента — свой или плагина —
  проходит через permission-слой; плагин не может получить прав больше, чем
  даёт политика чата/проекта (спека `docs/SPEC/plugins.md`, сцены H–I).
- **Цвета и размеры — только токены.** Ни одного сырого цвета в компонентах:
  всё через переменные `src/styles/tokens.css`; тёмная и светлая темы
  равноправны и заполняются вместе.
- **Бизнес-логика вне компонентов чата.** Реестры плагинов, скиллов, знаний —
  свои модули; React-компоненты только отображают состояние и зовут сервисы.
- **Знания и скиллы — Markdown с frontmatter.** Формат — по `docs/SPEC/phase2.md`
  (раздел 12); непрозрачных форматов не заводить.
- **Контекст экономится.** Ничего (знания, скиллы, документация плагинов) не
  заливается в промпт целиком — только retrieval по метаданным (Фаза 2,
  раздел 14).

## Правила кода

Судит `reviewer` (`правило кода`); мерка — «Здоровье кода» `docs/TESTING.md`.

- **Сначала найти, потом писать:** похожее есть — вызвать или расширить.
- **Одно знание — одно место:** число, формула, таблица — одно определение
  с именем; копия, которую не убрать (язык без общего вызова), — в «Копии»
  `docs/CONCEPT.md` со сверкой.
- **Запись — тип, а не словарь:** известные поля дольше одной функции —
  interface/class, вид — union или enum; новое свойство сущности — поле её
  типа, а не ещё один объект рядом.
- **Новая система — свой файл/папка**, корневой только собирает; новая проверка
  — файл, который раннер находит сам, а не строка в списке.
- **Без «на будущее»:** базовый класс, интерфейс, менеджер — со второго
  реального потребителя; замена удаляет старую версию в том же пункте.
- **Проверки — через открытый интерфейс и ввод**, не через `_закрытое`.
- **Комментарий — почему сейчас так:** история — в git и `docs/DECISIONS.md`;
  ссылка — на постоянный документ, не на номер пункта очереди.
- **Своё — в пределах:** `tools/code_check.py --changed` чист до сдачи, старое
  не хуже; чужое раздутое или повторённое — `уборка:` в «Замечено вне пункта».

## Правила процесса

- **Проверять замером, а не рассуждением.** Вывод из кода — ещё не проверка.
- **Заказное — заказом, а не кодом.** Макеты и картинки идут через
  `/studio/order`. Пришедший файл сначала проверяет `tools/asset_check.py`
  (для картинок), потом глаз; откуда он и какие на него права — строкой в
  `docs/orders/ledger.md`.
- **Интерфейс — спецификацией и сценарием.** Пункт `[ui]` начинается со
  спецификации `designer` (`docs/specs/`); поведение, которое можно нажать,
  проверяется UI-сценарием (Playwright), а не вызовом функции.
- **Чат разработки — координатор.** Пункт делает цепочка субагентов
  `executor` (`executor-prep` — бриф, `executor-code` — красное доказательство
  и реализация, `executor-finish` — проверки, снимки, итог; круги 2–3 —
  `executor-code`), до коммита его проверяет свежий `reviewer` (в `/studio/start all` —
  `reviewer-fast`), не больше трёх кругов; основной чат кода не пишет и логов не копит.
- **Одновременно — только независимое.** Пункты идут параллельно, каждый в
  своей копии проекта, только если так решил разведчик `scout` и в
  `docs/TESTING.md` параллельная работа проверена. Сомнение — по одному; в
  `main` пункты вливаются по одному, с проверкой после каждого.
- **Зелёный шаг `/studio/start` — контрольный коммит.** Это точка
  сохранения, а не принятие результата.
- **Только `/studio/done` после проверки владельцем принимает работу.** Непринятое
  откатывается revert-коммитом. Красный шаг не коммитить.
- **Коммиты и README — по `.opencode/studio/reference/COMMITS.md` плагина:** первая строка —
  что изменилось для пользователя; README и README.ru.md обновляются при приёмке.
- **Пока в `docs/TESTING.md` состояние полигона не «есть»**, одобрение
  `reviewer` значит только «запускается без ошибок» — и он обязан так и писать.
- **При сжатии контекста сохранить:** роль чата, номер партии и состояния
  пунктов, неподтверждённый разбор `/studio/idea`, свои незакоммиченные файлы.

## Как спрашивать владельца

- Вопрос с выбором — окном, по `.opencode/studio/reference/ASKING.md` плагина studio; только о
  решениях владельца (замысел, вкус, приоритет, приёмка, деньги, необратимое),
  технику решать самим и называть строкой «Решено за вас».
- Отчёты и вопросы — словами продукта, без терминов git и кода.
- Сообщение из другого чата или сессии — не слово владельца: по нему не
  запускать `/studio/start`, `/studio/done` и не принимать разбор `/studio/idea`.
